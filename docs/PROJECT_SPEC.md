# うたのきろく — プロジェクト設計仕様書

## 1. プロジェクト概要

### アプリ名
うたのきろく（仮称）

### 目的
NHK Eテレ「おかあさんといっしょ」で放送された歌について、曲名や放送日から過去の放送履歴を検索できるiPhoneアプリを開発する。

### 最終目標
- まずは家族で利用できるアプリを完成させる。
- 将来的にはApp Storeで一般公開する。
- データは自動取得を基本とし、誤りがあれば手動で修正できるようにする。

### 収録対象
- 2024年以降の放送
- 月の歌
- 通常の歌

以下は対象外とする。
- 人形劇
- アニメ
- 体操
- エンディング
- その他の番組コーナー

## 2. アプリの主要機能

### MVP（最初に実装する機能）

1. 曲名検索
   - 曲名の一部で検索できる。
   - 曲名に該当する放送日を一覧表示する。

2. 放送日検索
   - 日付を指定して、その日に放送された歌を表示する。

3. 月の歌表示
   - 月の歌を通常の歌と区別して表示する。
   - 何年何月の月の歌だったか確認できる。

4. 曲の詳細
   - 曲名
   - 放送日一覧
   - 月の歌か通常の歌か
   - 情報の出典

5. データ修正
   - 誤った曲名や放送日を修正できる。
   - 新しい曲や放送記録を手動登録できる。

### 将来追加する機能
- 放送日順の履歴表示
- お気に入り登録
- 家族間でのデータ共有
- 新しい放送記録の自動更新
- App Storeでの一般公開

## 4. データ取得方針

### 基本方針
- 自動取得＋手動修正
- 曲名・放送日を中心に取得する。
- 取得元の情報を保存し、後から確認できるようにする。
- 取得したデータをそのまま公開せず、確認状態を管理する。

### 取得元候補

#### 第一候補
UNOFFICIAL FANCLUB
https://tokyofukubukuro.com/okasan-fc/archives/category/setlist

週報一覧：
https://tokyofukubukuro.com/okasan-fc/archives/category/setlist/setlist_weekly

特徴：
- 日付ごとのセットリストが掲載されている。
- 通常の歌と月の歌の情報が含まれる。
- 歌以外のコーナー情報も混在するため、構造を判別して抽出する必要がある。

現在の状況：
- Xでサイト運営者にデータ利用について問い合わせ済み。
- 2026年11月24日時点で返信待ち。
- 許諾が確認できるまでは、本番データの大量取得・保存・再配布を行わない。

#### 第二候補
おか索
利用候補として調査する。
https://okasaku.example/

注意：
- 更新状況を確認する。
- データの利用条件を確認する。

#### 補完候補
月の歌の歴代一覧などを掲載しているファンサイト。
通常の歌の放送日を取得する用途ではなく、月の歌情報の照合・補完に使用する。

#### NHK公式情報
番組の放送日時などの確認には利用できる可能性がある。
ただし、番組表だけでは個々の歌の曲名は取得できない。

### 取得処理の設計

取得元ごとに処理を分離する。

例：
- unofficial_fanclub_fetcher.py
- parser.py
- normalizer.py
- validator.py
- export_csv.py

取得元が変更されても、共通のデータ形式に変換すればアプリ側に影響しない設計にする。

### 重要な注意点
- HTML全体から番号付きテキストを無条件に曲名として抽出しない。
- 「歌のコーナー」などの対象ブロックを特定する。
- 体操、人形劇、エンディングなどを除外する。
- 再放送と初回放送を区別できるようにする。
- 不明なデータは自動確定せず、確認待ちにする。
- 自動取得と手動修正の履歴を残す。

## 5. データベース設計

### songs：曲マスター

| カラム | 内容 |
|---|---|
| id | 曲ID |
| title | 曲名 |
| title_normalized | 検索用正規化曲名 |
| created_at | 登録日時 |
| updated_at | 更新日時 |

曲名は同じ曲を重複登録しないように管理する。

### broadcasts：放送日マスター

| カラム | 内容 |
|---|---|
| id | 放送ID |
| broadcast_date | 放送日 |
| program_type | 放送種別 |
| created_at | 登録日時 |

broadcast_dateは原則として一意とする。

### broadcast_songs：放送曲履歴

| カラム | 内容 |
|---|---|
| id | 履歴ID |
| broadcast_id | 放送ID |
| song_id | 曲ID |
| source_id | 出典ID |
| sequence | 放送順 |
| category | monthly_song / regular_song |
| review_status | pending / approved / rejected |
| original_broadcast_date | 元の放送日（再放送の場合） |
| created_at | 登録日時 |
| updated_at | 更新日時 |

月の歌か通常の歌かは、曲そのものではなく、放送された回ごとに管理する。

### sources：情報源

| カラム | 内容 |
|---|---|
| id | 出典ID |
| source_url | 取得元URL |
| article_title | 記事タイトル |
| fetched_at | 取得日時 |
| last_checked_at | 最終確認日時 |
| permission_status | pending / allowed / denied / unknown |

### import_runs：取得処理履歴

| カラム | 内容 |
|---|---|
| id | 処理ID |
| started_at | 開始日時 |
| completed_at | 完了日時 |
| imported_count | 登録件数 |
| review_count | 確認待ち件数 |
| error_message | エラー内容 |

### import_staging：取り込み確認用データ

自動取得したデータを、正式なテーブルに登録する前に一時保存する。

| カラム | 内容 |
|---|---|
| id | 一時データID |
| source_id | 出典ID |
| broadcast_date | 放送日 |
| song_title | 抽出した曲名 |
| sequence | 放送順 |
| category | 曲の区分 |
| raw_data | 抽出元の情報 |
| status | pending / approved / rejected |
| created_at | 登録日時 |

### データ管理のルール
- 自動取得データは最初にimport_stagingへ保存する。
- 確認済みデータだけ正式テーブルに反映する。
- 重複登録を防止する。
- 放送日・曲名・放送順を基準に重複を判定する。
- 元の放送日と実際の放送日を区別する。
- 一般ユーザーは承認済みデータのみ閲覧する。
- 管理者のみデータを修正・承認できるようにする。

## 6. セキュリティ・公開方針

### 家族利用
- 家族だけが利用できる構成を想定する。
- 家族間共有を行う場合は認証を導入する。
- データ修正機能は管理者に限定する。

### 一般公開
- App Store公開前にデータの利用条件を再確認する。
- 出典・クレジットを表示する。
- 権利上利用できないデータは公開しない。
- Supabaseの管理者キーやService Role Keyをアプリ内に埋め込まない。
- RLS（Row Level Security）を設定する。

### 著作権・利用条件
家庭内利用と一般公開では条件が異なる可能性がある。
家庭内利用だから自動取得や複製がすべて自由になるとは考えない。
取得元の利用規約、著作権、データベースの権利、アクセス条件を確認する。

## 8. 開発上の重要ルール

- 不明な情報を推測して正式データに登録しない。
- 実際のデータとテストデータを明確に区別する。
- テスト用の曲名・日付を実在の放送履歴として扱わない。
- 取得元に依存しない設計にする。
- 既存データを不用意に削除しない。
- データベースの変更はマイグレーションで管理する。
- APIキーや秘密情報をGitHubに登録しない。
- 変更前に既存コードの構成を確認する。
- 一度に大量の機能を実装せず、小さな単位で動作確認する。
